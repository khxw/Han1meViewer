## 2. 项目概览

项目是 Han1meViewer Remastered，Android Kotlin + Jetpack Compose 应用。

主要技术栈：

- Kotlin 2.3.x，Java 21
- Android Gradle Plugin 9.2.x
- Jetpack Compose + Material 3
- Navigation Compose typed routes
- ViewModel + StateFlow
- Retrofit 3 + OkHttp + kotlinx.serialization
- Jsoup HTML 解析
- Room + KSP
- WorkManager
- Coil 3
- Media3 ExoPlayer、JZVD、MPV

主要能力：

- 首页、搜索、视频详情、评论、播放
- 收藏、稍后观看、播放列表、在线历史
- 本地收藏与收藏分组
- 在线订阅和创作者中心
- 下载、下载分组和本地播放
- H 帧、共享 H 帧
- 首页栏目排序与隐藏
- 继续观看
- 随机视频
- 本地海报墙
- 网络设置、DoH、Hosts、代理和日志
- 自动系列归并

## 3. 用户明确要求与不可违反的约定

### 3.1 沟通与实现

- 默认使用简体中文回复。
- 项目技术文档要求最小正确修改。
- 文本文件使用 CRLF，文件末尾保留一个换行符。
- 页面状态优先使用 StateFlow。
- 一次性事件使用 SharedFlow 或回调。
- 网络和数据库访问不要直接写进 Composable。
- 列表分页和合并必须按稳定业务键去重。
- 不声称成功，除非已有编译、测试或构建证据。
- 用户对回归非常敏感，优先保守修改。
- **默认只构建 arm64-v8a（`-PfastBuild=true`）。只有用户明确要求“全量/5 个 APK/其它 ABI”时，才跑不带参数的 assembleRelease。用户曾明确指出这一点，不要重复违反。**

### 3.2 网络红线

- 不要随便切换域名。
- 不允许在遇到 403/429 时自动切换到其他域名。
- 域名切换必须保持为用户手动操作。
- 被限流时只允许冷却当前域名，避免继续重复请求。
- 手动更改网络、域名或站点配置后，允许重置限流冷却。

### 3.3 设置语义

- DoH 与应用内建 Hosts 必须保持互斥。
- 开启 DoH 时，应询问并关闭内建 Hosts。
- 开启内建 Hosts 时，应询问并关闭 DoH。
- DoH 摘要需要显示互斥提示。
- 该互斥限制曾在 1.1.100 被移除，随后按用户要求于 1.1.101 恢复。
- 1.1.103/2.1.0 仍保持互斥，不要因为修复视频 CDN 再擅自放开。

### 3.4 已明确移除的功能

- 全局迷你播放器已彻底移除。
- 不要重新添加迷你窗、迷你播放器按钮或相关状态。
- 海报墙必须保持为本地导出方案，不得为了封面批量请求大量视频详情页。

### 6.14 自定义 Hosts、DoH 与视频 CDN

现场观察到的事实：

- hanime1.me 使用 Cloudflare。
- 视频文件实际位于 vdownload.hembed.com。
- 自定义 Hosts 只对 HANIME_HOSTNAME 中的主站域名生效。
- 自定义 Hosts 必须在内建 Hosts 开启时才会优先使用。
- 视频 CDN 不属于 HANIME_HOSTNAME，自定义 Hosts 不会映射它。
- 低延迟不等于可用。2026-09-22 实测中：
  - 172.64.33.1：TCP/TLS 快，但视频页 HTTP 403
  - 108.162.192.1：TCP/TLS 快，但视频页 HTTP 403
  - 162.159.0.1：TCP/TLS 快，但视频页 HTTP 403
  - 172.64.229.154：HTTP 200，可生成 MP4 地址
  - 104.19.0.1：HTTP 200，可生成 MP4 地址
- vdownload.hembed.com 当时解析到 CDN77 地址，例如 195.181.172.2、195.181.172.5、195.181.172.6。
- AliDNS、DNSPod 对 vdownload.hembed.com 的解析曾返回可用 CDN77 地址。
- Quad9 在当时的当前网络下 SSL 连接失败。
- Google DoH、Cloudflare DoH 能解析，但延迟明显更高。

重要缺陷：

- ExoPlayer 当前使用 DefaultHttpDataSource。
- DefaultHttpDataSource 直接使用系统 DNS，不走应用 HDns。
- 因此应用内 DoH 无法影响 ExoPlayer 的视频 MP4 请求。
- 这解释了“DoH 配置了但视频仍然加载失败”。
- 尚未实施的候选修复：
  - 引入 media3-datasource-okhttp
  - 使用 OkHttpDataSource.Factory，并注入应用的 HDns/OkHttpClient
  - 或使用系统 Private DNS/VPN，使播放器也走同一 DNS
- 如果后续修复此项，必须同时验证主站单测、播放、下载、限流和 DoH/内建 Hosts 互斥逻辑。

### 6.39 网络诊断的样本来源与线路判定修正（2.1.52）

- 问题：原 CDN 实测依赖"观看历史 → 联网解析 watch 页"，一旦主站不可达就取不到样本，而主站不可达恰恰是用户最需要诊断的场景之一。
- 修复：样本来源改为三层兜底。
  1. `HanimeDownloadEntity.videoUrl`（下载记录里保存的真实 CDN 地址）—— 完全不需要联网解析，主站挂了也能测；
  2. 观看历史 → 实时解析 watch 页；
  3. 都没有则明确提示缺少样本。
- 判定口径修正：对"线路是否可达"而言，**只要收到任何 HTTP 响应（含 403/404）就说明线路是通的**，状态码只反映业务层；只有完全无响应（超时/连不上/DNS 失败）才算线路不通。
- 结论区分随之调整：
  - CDN 完全无响应 → 线路被封锁，建议开代理；
  - CDN 有响应但状态码异常 → 线路可达、请求被拒（签名过期或来源校验），建议换域名或重新登录，而不是开代理。
- 新增字符串 `network_diagnostics_cdn_sample_from` / `_sample_download` / `_sample_history` / `_rejected_business`，并改写 `network_diagnostics_conclusion_cdn_rejected`（四语言同步）。
### 6.40 网络诊断的两处缺陷修复与样本兜底（2.1.53 ~ 2.1.54）

**2.1.53：内置 Hosts IP 延迟全部误报超时**

- 现象：同样一批内置 Hosts IP，在"查看节点延迟"里部分可用，在网络诊断里却全部超时。
- 根因：`measureTcpDelay` 被调用在 `viewModelScope.launch` 的默认 Main 线程上，`Socket.connect` 触发 `NetworkOnMainThreadException`，又被 `catch (_: Throwable)` 静默吞掉，于是每项都返回 -1（超时）。与样本来源无关。
- 修复：把 TCP 探测放进 `withContext(Dispatchers.IO)`，并在 catch 中写入 HLumberjack，避免同类问题再次静默失败。

**2.1.54：样本兜底补第三层 + 措辞**

- 新增第③层样本来源：没有下载记录、也没有观看历史时，从首页 `latestHanime` 取一个 videoCode 再解析 watch 页，避免"既无下载又看不了视频"时直接失去样本。

- 样本缺失文案改为"无法评估视频线路：没有可用的样本"，并新增结论 `network_diagnostics_conclusion_cdn_no_sample` 与建议 `network_diagnostics_suggest_play_then_retry`。

### 6.42 DNS 污染判定口径修正（2.1.56）

- 原实现：`checkSystemDns` 只要发现解析结果**不在 Cloudflare 网段**就标记"疑似遭污染"。该前提是"hanime1 系列域名一定托管在 Cloudflare"，并不总成立。
- 误报来源：站点更换 CDN、候选中 `javchu.com` 等域名本身不在 Cloudflare、CNAME 转到其他 CDN、返回非 `2606:4700::/32` 的 IPv6。
- 新口径：默认认为解析正常，只有命中"明确不可能合法"的地址才报警——
  - 回环 / 未指定 / 私网地址（`isLoopbackAddress` / `isAnyLocalAddress` / `isSiteLocalAddress`）；
  - GFW DNS 投毒常用的 Facebook 网段：`31.13.x`、`69.171.x`、`157.240.x`。
- 状态映射：全部命中 → FAIL；部分命中 → WARN；无命中 → PASS。解析结果展示数量由 3 个增至 4 个，便于人工核对。
- `isCloudflareAddress` 已移除，改为 `isPollutedAddress`。
- 文案同步：`network_diagnostics_dns_polluted` 由"不在 Cloudflare 网段"改为"含疑似投毒／劫持地址"（四语言）。

### 6.44 修复"未同意须知却已开启内置 Hosts"（2.1.58）

- 现象：首次启动时"同意使用须知 → 开启内置 Hosts → 重启"这条链路走完后，重启回来发现内置 Hosts 已被开启，但使用须知又重新弹出（记录显示尚未同意），状态自相矛盾。
- 根因：`SharedPreferences.edit {}` 默认使用 `apply()`，是**异步**落盘。`ActivityManager.restart(killProcess = true)` 会在写入完成前杀掉进程，而两次写入（`usageNoticeAccepted` 与 `USE_BUILT_IN_HOSTS`）落盘时机独立，结果一个成功、一个丢失。
- 修复：
  - 新增 `Preferences.markUsageNoticeAcceptedSync()` / `markHostsAutoPromptShownSync()` / `setUseBuiltInHostsSync()`，内部统一使用 `edit(commit = true)` 同步落盘。
  - `MainActivityContent` 中须知"同意"、Hosts 弹窗"开启并重启"与"暂不开启"三处全部改用同步写入。
- 顺带修复既有同类隐患：`NetworkSettingsRoute` 中手动开关内置 Hosts 的写入原本也是 `apply`，保存后紧接着就是重启确认，同样可能丢失；现已改为 `commit = true`（域名切换路径此前已经是 `commit = true`，无需改动）。
- 经验：**任何"写完立刻重启进程"的持久化都必须用 commit，不能用 apply。**
### 6.45 内置 Hosts 开启时机收紧与回读校验（2.1.59）

用户再次明确需求：**必须"读完使用须知 → 同意 → 弹出 Hosts 弹窗 → 用户点击开启并重启"，才允许开启内置 Hosts。**

- 代码核实：全项目搜索 `USE_BUILT_IN_HOSTS`，写入点只有三处——
  1. `NetworkSettingsRoute` 设置页手动拨动开关（用户主动操作）；
  2. `NetworkSettingsRoute` DoH/Hosts 互斥确认弹窗（用户点确认）；
  3. `Preferences.setUseBuiltInHostsSync()`，仅由本次新增的 Hosts 弹窗"开启并重启"回调调用。
- 流程核实：`UsageNoticeDialog` 的 `onAccepted` 只做两件事——同步写入"须知已同意"、把 `showHostsAutoPrompt` 置为 true；**不写任何 Hosts 开关**。写入只发生在 `ConfirmDialog` 的 `onConfirm` 里。
- 新增回读校验：`setUseBuiltInHostsSync(true)` 之后读取 `Preferences.useBuiltInHosts`，只有为 true 才执行 `ActivityManager.restart`；写入未生效则不重启，避免再次留下不一致状态。
- 该弹窗 `cancelable = false`，用户必须明确选择"开启并重启"或"暂不开启"；"暂不开启"只记录已询问，不修改开关。
### 6.46 内置 Hosts 的强制闸门与残留自愈（2.1.60）

用户反馈："打开软件后弹出使用须知，过几秒就自动开内置 Hosts。" 全项目复查后确认：**代码中不存在任何定时或自动开启 Hosts 的逻辑**，该键只有三处写入点，且均需用户主动操作。用户看到的应是旧版本（2.1.57 及之前）`apply()` 落盘被重启截断后遗留的不一致状态。

为彻底杜绝该类问题，本版新增两道防护：

1. **强制闸门（写入层）**：`Preferences.setUseBuiltInHostsSync(true)` 内部先判断 `usageNoticeAccepted`，为 false 时直接返回不写入。即使将来有新代码路径调用它，也无法在"未同意使用须知"时打开内置 Hosts。
2. **残留自愈（启动层）**：新增 `Preferences.repairInconsistentHostsState()`，在 `MainActivityContent` 中通过 `remember { ... }` 在进入界面前执行一次；若检测到 `!usageNoticeAccepted && useBuiltInHosts` 这种不可能的正常组合，则同步把 Hosts 复位为关闭。

因此用户**无需手动清数据**：安装 2.1.60 后首次启动即会自动修正遗留状态，然后正常走"同意须知 → 弹窗 → 点击开启并重启"的流程。
### 6.47 网络诊断结论补缺口与建议分级（2.1.61）

- 用户指出：DNS 解析正常、主站连接失败时，诊断给出的是"建议换域名或网络环境"，属于误报。
- 根因：`buildConclusion` 中所有 `mainOk == true` 的分支都不匹配这个组合，最终掉进兜底的 `else`（原本留给"结果不完整"的情况）。

### 6.48 修正升级后内置 Hosts 被关闭（2.1.62）

- 用户反馈：老版本用户安装新版本后，内置 Hosts 被关掉了，需要重新手动开启。
- 根因：2.1.60 为解决"未同意须知却已开启 Hosts"的残留状态，加入了 `repairInconsistentHostsState()`，其处理方式是**把 Hosts 复位为关闭**。这会把正常使用 Hosts 的老用户的设置一并清掉。

### 6.69 漫画详情 404 修复（2.1.84）

- 现象：从视频详情点「原作漫画」进入漫画详情页，显示加载失败 404。
- 原因推断：ComicService 之前用 HANIME_BASE_URL（用户当前选择的镜像域名）+ 相对路径 comic/{id} 请求；漫画页并非在所有镜像域名下都存在，因此拼出的 URL 会 404。
- 修复：ComicService 改为 @GET + @Url 绝对地址；ComicRoute 增加 url 字段，VideoRouteActions.openOriginalComic 把站点给出的原始漫画链接整条透传；只有 url 为空时才回退用 HANIME_BASE_URL 拼 comic/{id}。
- 同时把实际请求的 URL 拼进错误信息（<错误> · <url>），万一仍失败可直接看到请求的是哪个地址。
- 注意：图片 CDN（i.nhentai.net / t2.nhentai.net）是第三方域名，不在 HANIME_HOSTNAME 内，自定义 Hosts 不覆盖它。
- 2026-10-12 实测结论（重要）：用户网络下 hanimeone.me 的**系统 DNS 被投毒**（HDns 报 all DNS results are polluted），且**内建 Hosts 的 Cloudflare IP + SNI=hanimeone.me 会被 Connection reset**。最终**开启 VPN（全局）后可正常加载**。结论：漫画域名必须被 VPN/代理覆盖；Hosts 只能解决解析、解决不了 SNI/链路。

### 6.80 接上 Mihomo 配置层（2.1.112）

- 目标：**Clash YAML 原样喂给内核**，从而原生支持 hysteria2；并恢复真实测速、自动拉起、切换节点。
- 已核实的 gobind Java API（`com.follow.clash.core.mobile.Mobile`）：
  `touch()` / `quickSetup(String initParams, String setupParams, ResultHandler)` / `invokeMethod(String, ResultHandler)` /
  `startListener()` / `stopListener()` / `setEventListener(ResultHandler)` / `getTraffic(boolean)` / `resetNetwork()` /
  `startTun(int, TunHandler, ...)` / `stopTun()` / `updateDns(String)` / `forceGC()`。
  回调接口是 `ResultHandler{ void onResult(byte[]) throws Exception }`（gobind 把 Go 的 `error` 返回值变成 Java 的 throws）。
- 内核启动流程（读 `Clash.Meta/core` 源码确认）：
  `quickSetup` → `handleInitClash`（`SetHomeDir` + `sdkVersion` + `isInit=true`）→ `isRunning=true` →
  `handleSetupConfig` → `applyConfig`：读 **`<home-dir>/config.yaml`** → `executor.ParseWithBytes` →
  `hub.ApplyConfig` → `patchSelectGroup(selected-map)` → `updateListeners`（起 mixed/http/socks 入站）。
  配置写坏时内核会**回退到内置默认配置**（里面没有节点），表现就是「每个节点都测速超时」，日志会写
  `config apply failed, falling back to the built-in default`。
- 生成的配置（`mihomo/MihomoConfig.kt`）刻意保持最小：
  ```yaml
  mixed-port: 10808
  mode: global          # 走内核算术自动创建的 GLOBAL 分组，配置里不枚举节点名
  ipv6: false
  unified-delay: true
  find-process-mode: off
  dns: { enable: false }
  proxies: <订阅原文原样透传>
  ```
  - 不用 `proxy-groups` 自己列节点名：`config.parseProxies` 里名字对不上会让**整份配置**加载失败，
    而 `mode: global` 时内核会自动建 `GLOBAL` 选择器（包含全部节点 + DIRECT），正好够用。
  - 不写规则：没有 GEOIP/GEOSITE，内核就不会去下载 geo 数据库。
  - 只有一条 `MATCH` 也不需要规则——App 侧只把被墙域名指向这个端口（`ServiceCreator.ComicProxySelector`）。
- 切节点：`invokeMethod({"method":"changeProxy","arguments":{"group-name":"GLOBAL","proxy-name":<名字>}})`，
  返回 `{message, changed}`，`message` 非空即内核不认这个节点名。
- 测速：`invokeMethod({"method":"asyncTestDelay","arguments":{"proxy-name":…,"timeout":5000}})`，
  回调里 `result.value` 是毫秒；内核用 -1/-2 表示超时/失败。

### 6.81 修「内核无响应（超时）」（2.1.113）

- 现象：2.1.112 装到真机，点节点 → 「启动失败：内核无响应（超时）」（`quickSetup` 30s 回调超时）。
- 根因（2.1.112 自己的写法）：`ComicProxyManager.startBlocking` 在 `quickSetup` **之前**调了一次
  内核 `shutdown`，而且是不等回调的异步调用。内核侧 `handleShutdown` 的第一步就是
  `configMu.Lock()`，而 `quickSetup` 里的 `handleInitClash` 也要这把锁——两者相撞，
  `handleInitClash` 卡在锁上，`quickSetup` 的 goroutine 永远到不了 `answer(...)`，
  于是 Java 侧只看到「回调一直不来」。**第一次启动也走了这条路径**（那时 `running=false`，
  但代码无条件调 shutdown），所以第一次就必现。
- 决定性证据来自 FlClash 自己的生产代码，两处：
  - `lib/core/interface.dart`：Dart 侧根本不用 native 的 `quickSetup`，而是分步
    `invokeMethod(initClash, {home-dir, version})` → `invokeMethod(setupConfig, …)` → `startListener`；
  - `ServiceStateMachine.kt:369` 的 `initParams()` 正是 `{"home-dir":…, "version":sdkInt}`，和我们一致；
  - 另外 `ServiceController` 的「停止」用的是 `Core.stopListener()`，不是 `shutdown`。
    也就是说 FlClash 把 `shutdown` 留给「整进程退出」，启动路径上从不调它。
- 改法：
  1. **启动路径彻底删掉 `shutdown`**；断开改用 `stopListener`（只关端口、保留已加载的配置，可再起）。
  2. 启动改成 `probe(getIsInit) → initClash → 写 config.yaml → setupConfig → startListener → 端口校验`。
     分步之后每一步都能单独报错，不再是 `quickSetup` 那种黑盒。
  3. `MihomoCore` 新增 `sealed interface CoreReply`：`NoResponse`（回调超时）/ `Failure`（内核报错）
     / `Success`。**「回调不通」和「内核报错」必须分开报**，否则下次还是只能看到「超时」。
  4. 加 `getIsInit` 探针：它毫秒级返回就说明 gobind 的 Java 回调是通的，失败时能直接给出这个结论。
  5. 加 10808 端口轮询（最多 6s）：`startListener` 返回 true 不代表端口已经 bind，探到才算出结果。
     对应 `ServiceCreator.ComicProxySelector` 那个「端口没监听就直连」的兜底。
- 关键返回语义（容易踩）：`setupConfig` 走的是 `withMessage` 包装，**成功时 `result` 是空字符串，
  失败时把错误文本放在 `result` 里**（不是 `error` 字段）。所以判读要用 `CoreReply.setupConfigError()`。
- 验证：compileDebugKotlin / testDebugUnitTest（13 条全过）/ assembleRelease -PfastBuild=true 通过；
  arm64 包 97,982,304 字节，SHA-256 `74B6A2AC6BF146F46C60EC0C075153E140BEFA14A6928F15992B5A2718E9741B`。
- 真机结果：点「测速」时内核还没启动，见到「节点全部失败，已自动更新订阅」——见 6.82。

### 6.82 修「没启动内核时测速 → 误报节点全部失败」（2.1.114）

- 现象：用户导入订阅后直接点「测速」，状态行报「节点全部失败，已自动更新订阅」。实际原因是

  1. `testDelays` 在测之前先 `ensureRunningForTest()`：优先上次选中的节点，其次第一个非日本节点，

     把 `ComicProxyManager.lastMessage`（真正的失败原因）显示出来，不做自动更新订阅。
  3. 设置页在测速后刷新 `running` 状态；如果是测速把内核顺带拉起来的，状态行会提示「已启动：X」。
  4. 只有内核确实在跑、且所有节点都 `<= 0` 时才走原来的「可能订阅过期」逻辑。
- 新增单测：`delayTestNeverReportsFailureWhenItCannotTest`——空输入必须返回空 map，

### 6.85 状态卡时间被省略 + 节点行 55dp + 点空白收起输入（2.1.117）

- **状态卡「信息不完整」的根因**：状态卡第 3 行是
  `Text("socks 127.0.0.1:10808") + Spacer(weight(1f)) + Text("订阅更新于 …", weight(1f, fill=false))`。
  同一行里有**两个 weight 子项**，Flex 会先把剩余宽度**平分**给它们，所以时间文本只拿到一半宽度，

  未更新过时给空串占位，保持 socks 文本仍靠左。
- **教训（本项目里已经踩两次）**：同一行里既放 `Spacer(Modifier.weight(·))` 又放带 `weight` 的文本，
  两者会平分剩余空间导致文本被过早省略。要么只留一个 weight，要么让文本自己 `weight(1f)` 并设对齐。

### 6.87 代理页三张容器卡片的主题适配（2.1.119）

- 需求：状态卡 / 订阅卡 / 节点卡（**容器卡片**，不是里面的节点行）在不同设备和不同主题下底色显示有问题。
- 根因：三张卡用的是 `ElevatedCard(colors = CardDefaults.elevatedCardColors())`。
  它靠 **elevation 阴影 + `surfaceTint` 叠色** 表达层级，这套机制在下列场景都会失真：
  - **AMOLED 纯黑**（`ThemePresets.toAmoled()` 把 surface 置黑）：阴影在纯黑上看不见，
    卡片与背景几乎糊在一起；
  - **自定义高饱和主题**：`ThemePresets` 的容器色差异大（例如红色预设 `primaryContainer = #EB0000`），
    tint 叠色会把卡片底色带偏，看起来发灰/发脏；
  - **动态取色**：系统色板的 tone 层次与预设不同，同一段代码在不同机器上观感不一致；
  - 各厂商 ROM 对 Compose 阴影的渲染本身也不一致。
- 改法：新增本地 `ProxyCard` 组合函数，改用**与设置页 `SettingItem.kt` 里 `settingCard` 完全一致**的画法：
  ```kotlin
  Surface(
      modifier = Modifier.fillMaxWidth(),
      shape = RoundedCornerShape(16.dp),
      color = MaterialTheme.colorScheme.surfaceContainerLow,   // 显式底色，不靠 tint
      contentColor = MaterialTheme.colorScheme.onSurface,
      border = BorderStroke(1.dp, MaterialTheme.colorScheme.outlineVariant.copy(alpha = 0.42f)),
  )
  ```
  显式底色 + 描边与主题无关：浅色、深色、AMOLED、任意预设、动态取色下都有清晰边界。
  三处 `ElevatedCard { Column { … } }` 改为 `ProxyCard { Column { … } }`（保留内层 Column，改动最小）。
- 层级关系：页面 `background` → 卡片 `surfaceContainerLow` → 未选中节点行 `surfaceContainerHigh`
  → 选中节点行 `primaryContainer`，四个 tone 层次在各主题里都成立。
- 顺带修（同一类主题问题）：选中节点行的文字原来用 `onSurface`，但底色是 `primaryContainer`。
  在红色预设里 `primaryContainer = #EB0000`、`onPrimaryContainer = #FFFFFBFF`，
  用 `onSurface`（深色文字）对比度不足。现在选中行统一：
  - 标题 `onPrimaryContainer`
  - 服务器行 `onPrimaryContainer.copy(alpha = 0.82f)`
  - 延迟/状态 `onPrimaryContainer`（绿/黄/红语义色在高饱和容器上对比度不可控）
  - 左侧竖条 `onPrimaryContainer`

  assembleRelease -PfastBuild=true 通过；arm64 包 97,982,264 字节，
  SHA-256 `6D80331F4961E1712C91A2C23BB8E4A32B12AD748B1085F64C24D20967FB0E93`。

### 6.88 内置代理接管内置 Hosts 的域名（2.1.120）

- 需求：内置 Hosts 失效时，内置代理要能顶替它。
- **原先的缺口**：

- 新增 `logic/network/BuiltInProxyHosts.kt`：域名名单以 `HanimeConstants.HANIME_HOSTNAME`
  为唯一来源（避免两处漂移）+ 原有的 nhentai 系列；**后缀匹配**，所以 `www.hanime1.me`
  这类子域名也会命中；`trimEnd('.')` 兼容 FQDN 尾点；大小写不敏感。
- 接入两处选择器：
  1. `HProxySelector`（`ProxySelector.setDefault` 的实例，`hClient` 用它，**ExoPlayer 的
     `DefaultHttpDataSource` 也走它**）：手动 HTTP/SOCKS 代理优先；没配手动代理时，
     若命中名单且本地端口在监听 → 返回本地 SOCKS。
  2. `ServiceCreator.ComicProxySelector`（`comicClient`）：改成同一份名单 + 同一个存活探测，

  `InetSocketAddress.createUnresolved(host, port)`，**不做本地 DNS**；域名原样交给代理端解析出站。

- 存活探测收敛到 `ComicProxyManager.isLocalProxyListening()`（5 秒缓存 + `running` 快速短路），

- 刻意**不**纳入 `vdownload.hembed.com` 等视频 CDN：Hosts 从来不管它们，走代理会额外烧订阅流量。
  MPV 的 `http-proxy` 也没有改（同样原因）。若以后确实需要，再单独加。

### 6.89 Cloudflare 验证链路的三个实际缺陷（2.1.121）

- 现象：收到提示「当前网络环境无法通过验证…建议切换至更干净的 IP」。
  这条文案出自 `NetworkRepo.throwRequestException()`：**HTTP 403 + 正文含 `Just a moment`** 时抛出。
- 查出三个独立缺陷（都不是「换个 IP 就好」那么简单）：

  1. **拦截器可能根本不打开验证页**。
     `CloudflareInterceptor` 原条件是 `code == 403 && header("cf-mitigated") == "challenge"`。
     Cloudflare 在部分节点/规则下**只回 403 + "Just a moment" HTML、不带这个响应头**，
     于是拦截器不触发、`CloudflareActivity` 不打开，用户只能看到报错文案。
     改法：条件里加一条 `response.peekBody(8KB).string().contains("Just a moment")`
     （`peekBody` 不消费正文，`runCatching` 包住防止二进制响应抛异常）。

  2. **换节点后旧 `cf_clearance` 必然失效**。
     `cf_clearance` 与「出口 IP + User-Agent」绑定。用户在代理页换节点后，
     `Preferences.cloudFlareCookie` 仍会被 `HCookieJar` 附加到请求上，CF 判定环境不一致 → 403 循环。
     改法：`ComicProxyManager.startBlocking()` 里比较 `selectedNodeName` 与目标节点，
     **节点名变化时清空 `cloudFlareCookie` + `cloudFlareUserAgentOverride`** 并
     `ServiceCreator.rebuildOkHttpClient()`。只在节点真正变化时清，避免每次启动都丢验证。

  3. **关闭验证页会把请求线程永久挂住**。
     `CloudflareActivity.onClose` 只 `finish()`，但 `CloudflareInterceptor` 在 `latch.await()` 上等
     `CloudflareActivity.onFinished`。用户不完成验证直接关闭 → latch 永不 countDown →
     该请求永久阻塞（后续并发请求也排队）。
     改法：`onDestroy()` 里 `onFinished?.invoke(); onFinished = null` 放行等待者，
     请求重试后拿到 403 再正常抛错。

- 文案：新增 `cloudflare_proxy_challenge`（四语言）。代理运行时报这条
  （指向「换节点 / 手动导入 cf_clearance」），否则仍报原来的 `cloudflare_network_mismatch`
  （指向内置 Hosts 的解析不一致）。
- **遗留限制（重要）**：验证 WebView 走代理依赖 `HProxySelector.rebuildNetwork()` 写的那组
  Java 系统属性（`proxySet/proxyHost/proxyPort`）。这是项目原有的 hack，并非所有 WebView 版本都认。
  如果真机上 WebView 与 API 仍然从**不同出口 IP**出去，就会继续循环验证。
  彻底方案是引入 `androidx.webkit` 的 `ProxyController.setProxyOverride(...)`（API 29+），
  把 WebView 也固定到 `127.0.0.1:10808`；但当前离线构建环境没有该依赖缓存，本次未引入。
- 验证：compileDebugKotlin 无警告；testDebugUnitTest（18 条全过）；
  assembleRelease -PfastBuild=true 通过；arm64 包 97,984,040 字节，
  SHA-256 `E6E5808DBAD481E23340FD3D7A6712CA1B3A50F68AB5A56E5D65B7BD086C2215`。

### 6.97 播放卡顿的配置原因（2.1.130）

- 用户反馈：有时候播放视频一卡一卡的，问是不是网络原因。
- 结论：**网络抖动是诱因，但播放器配置把抖动放大了**。默认内核是 ExoPlayer
  （`Preferences.switchPlayerKernel` 默认 `HMediaKernel.Type.ExoPlayer`）。
- 查到的两处具体问题：
  1. **ExoPlayer 缓冲参数全是默认值**。`DefaultLoadControl.Builder()` 的三行调参都被注释掉了，
     实际生效的是 `min=50s / max=50s / 起播 2.5s / 重缓冲后 5s`。
     起播只要 2.5s 缓冲，网络一抖就进入重缓冲；重缓冲后 5s 就恢复播放，
     若带宽仍不足会立刻再次卡——表现为连续「一卡一卡」。
     改为 `20s / 60s / 4s / 10s`，并 `setPrioritizeTimeOverSizeThresholds(true)`：
     宁可多等一次 10s 缓冲，也不要反复小卡。
  2. **HTTP 数据源没有任何自定义超时**。`DefaultHttpDataSource.Factory()` 默认
     connect/read 都是 **8 秒**，弱网或跨境 CDN 很容易被误判超时后重连，造成周期性卡顿。
     改为 connect 15s / read 15s，并 `setAllowCrossProtocolRedirects(true)`
     （CDN 可能把 http 跳到 https，默认不允许跨协议跳转）。
- MPV 内核另有一个直接原因：`cache-pause` 被设成了 **`no`**，
  缓存一空就继续硬播（只能卡画面/跳帧）。改为 `yes` —— 缓存不足时暂停等缓冲。
- 仍未解决的限制（不是本次引入）：
  - **ExoPlayer 不吃应用的 `HDns`**（内置 Hosts / DoH）。它走 `HttpURLConnection` + 系统 DNS，
    所以 CDN 域名可能解析到不理想或污染过的 IP，这是卡顿的另一个潜在来源。
    彻底解决需要换成基于 OkHttp 的 `DataSource`（依赖 `media3-datasource-okhttp`）。
  - 视频 CDN 本身的质量、运营商跨境链路、设备解码能力（`mpvHwdec` / `mpvFramedrop`）
    仍会影响流畅度。

### 6.103 修「刷新还是那几个重复视频」（2.1.139）

- 现象：随机视频刷新后仍然是同样那批内容。
- 根因（可量化）：随机池原本只有 **首页每个分类的一页**（约十几条），
  而 `MAX_VIDEOS = 24` 一次就要抽 24 条。
  **池子比一次抽取量还小** → 每次刷新几乎必然把整个池子重新洗一遍。
  「避免最近播放」在这种池子大小下也完全失效。
- 改法：
  1. **扩池**：对每个选中的分类额外抓取搜索结果的第 2、3 页，与首页列表合并去重。
     分类 → 搜索参数映射与 `HomePageMappers` 一致：
     `LATEST_HANIME → genre=裏番 / sort=最新上傳`、
     `SHORT_EPISODE → genre=泡麵番 / sort=最新上傳`、
     `THREE_DCG → genre=3DCG / sort=最新上傳`。
     多个来源用 `coroutineScope + async` 并行抓取；**任一分页失败只返回空列表**，
     不会影响首页列表兜底。
  2. **LRU 回收**：
     ```kotlin
     val recentOrder = recentVideoCodes.withIndex().associate { (i, code) -> code to i }
     val unseen = candidates.filterNot { it.videoCode in recentOrder }.shuffled()
     val recycled = candidates.filter { it.videoCode in recentOrder }
         .shuffled()
         .sortedByDescending { recentOrder[it.videoCode] ?: Int.MAX_VALUE } // index 越大越旧
     return (unseen + recycled).take(MAX_VIDEOS)
     ```
     也就是「先抽没出现过的；池子不够时才回收，且优先最久没出现的」，
     不会再出现「刚刷新就重复上一轮」。
  3. `MAX_RECENT_VIDEO_CODES` 120 → 240，覆盖更大的池子。
- 踩坑：`PageLoadingState.NoMoreData` 是**没有 `info` 的 data object**
  （与 `PageState.NoMoreData(info)` 不同）；分页解析里不能对它取 `info`，
  改为 `if (state is PageLoadingState.Success) state.info else emptyList()`。
- 验证：0 警告 / 0 错误；testDebugUnitTest（12 条全过）；
  assembleRelease -PfastBuild=true 通过；arm64 包 38,935,797 字节，
  SHA-256 `C28FD2AAA1EEC39FACD14FAF646D53AD0099F26655FB046C9B37BCBB0EB69E68`。

### 6.104 随机页卡片大小 + 真·重复根因（2.1.140）

- 真机日志（v2.1.139）关键结论：
  - `GET /search?page=2&genre=...&sort=最新上傳` 全部 **200**（第 2、3 页都成功）→ 扩池请求本身没问题；
  - 紧接着出现 **30+ 个 `GET /watch?v=...` 200** → 这是 `verifyUnknownTags` 在逐个拉详情校验屏蔽标签；
  - 而 `verifyUnknownTags` 的循环条件是 `while (verified.size < MAX_VIDEOS)`，
    也就是说**标签校验把随机池截断成了 24 条** = 一次展示量，
    且每次刷新都按同样顺序校验同一批 → **每次都返回同样那 24 条**。
    这才是「刷新还是那几个」的真正原因（搜索分页是好的）。
- 另外一个独立问题：`RandomVideoGrid` 里
  `isHorizontalCard = video.itemType == HanimeInfo.NORMAL`，
  `true` 用 16:9 横图、`false` 用 3:4 竖图；随机池里两种 itemType 混在一起，
  网格就出现「有些卡片变大」。改为**统一 `true`**。
- 改法（`RandomVideoViewModel`）：
  ```kotlin
  private val tagVerificationCache = mutableMapOf<String, Boolean>() // code -> blocked
  private var tagCacheSignature: Set<String> = emptySet()

  private const val MAX_TAG_FETCH_PER_REFRESH = 30
  private const val MAX_VERIFIED_POOL = 120
  ```
  - 命中缓存直接复用；每次刷新最多补抓 30 个未知详情；
  - 校验池上限从 `MAX_VIDEOS(24)` 提到 `MAX_VERIFIED_POOL(120)`；
  - 屏蔽标签变化时（`blockedTags != tagCacheSignature`）自动清空缓存；
  - 拉取失败不写缓存，下次刷新重试。
- 效果：第 1 次刷新仍会拉 ~30 个详情页；之后每次只需补抓少量未知项，
  池子会逐步扩到 ~120 条，重复明显减少（120 / 24 = 5 轮不重复）。
- 新增日志（设置 → 日志可见）：
  - `RandomVideo 随机池: N 条, 来源=[...]`
  - `RandomVideo <source> 第 X 页: N 条` / `第 X 页拉取失败: ...`
  - `RandomVideo 标签校验: 候选 N 条, 可用 M 条`

### 6.112 修 Cloudflare 验证页未开始就退出（2.1.148）

## 10. 已知限制和待办

### 10.1 最高优先级

- ExoPlayer 播放请求不走应用 HDns/DoH。
- 自定义 Hosts 不覆盖 vdownload.hembed.com。
- 低延迟 Cloudflare IP 可能返回 403，不属于可靠播放节点。

### 10.2 系列归并

- 只有标题包含明确集数或前后篇标记时才会归并。
- 完全没有编号的系列不会自动识别。
- 同一集存在多个不同视频代码时，只保留优先级最高的一条。
- 缺失集只在已识别的最小集数到最大集数之间计算。
- 自动连播只在从“系列”页面进入并带有 autoPlayNextEpisode 标记时生效。

### 10.3 下载

- MP4 合并、封面嵌入和元数据嵌入依赖自定义 box 解析。
- 下载数据库、SAF 和私有存储路径都涉及高风险区域。
- 后续修改必须同时跑 EmbeddedVideoMetadataTest。

### 10.4 网络

- 403/429 冷却逻辑依赖当前域名策略。
- 如果未来增加自动换域名，属于违反用户红线的行为。
- 更改 DoH、Hosts 或域名设置后，应该重建网络并清空不必要的 DNS/限流缓存。

### 10.5 内置代理（已移除）

- **内置 Mihomo 代理已在 2.1.122 整体移除**（用户决定放弃），相关历史见 6.78 ~ 6.96。
- 现在只剩**手动代理**（设置 → 网络设置里的直连 / 系统 / HTTP / SOCKS），
  以及内置 Hosts / 自定义 Hosts / DoH。
- 不要再把 Mihomo 的内核限制当成现行待办；若将来重启内置代理，先读 6.79 ~ 6.90 的踩坑记录
  （尤其「启动路径绝不调 shutdown」和 `CoreReply` 的两类失败语义）。

7. 全局搜索 `MainDrawerDestination`，确认没有遗漏的显式列表或 when 分支。

每次修改前：

- 阅读 README_TECH.md。
- 确认需求是否触犯网络红线。
- 确认是否会重新引入已移除功能。

- 保持 CRLF 和末尾换行。
- 运行 compileDebugKotlin。
- 运行 testDebugUnitTest。
- 检查 git diff 和残留调试输出。
- 递增 patch 版本。
- 构建 assembleRelease（默认加 -PfastBuild=true，只出 arm64-v8a；用户要求全量时才不加）。
- 验证 APK 的签名、版本、ABI 和 16 KB 对齐（默认只验 arm64；全量时验 5 个）。
